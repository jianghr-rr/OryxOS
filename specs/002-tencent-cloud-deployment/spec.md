# Feature Specification: 腾讯云单机安全部署与运维体系

**Feature Branch**: `002-tencent-cloud-deployment`
**Created**: 2026-11-18
**Status**: Clarified (Ready for Plan)
**Input**: User description: "将 OryxOS（单机 Spring Boot Fat JAR + SQLite + /admin/ 管理台，默认监听 127.0.0.1:8080 且无内置登录认证/RBAC）通过 GitHub Actions CI/CD 安全部署到腾讯云单机服务器，覆盖访问安全边界、Java 21 运行环境、systemd 常驻与开机自启、工作区数据与程序包分离、日志与 SQLite 备份、安全发布与回滚策略、敏感凭证零入库约束（仅存 GitHub Secrets 与服务器 0600 文件），以及可选的 DeepSeek + 飞书 Webhook 定时推送上云。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 安全上线与访问边界控制 (Priority: P1)

运维人员将 OryxOS 单机服务部署到腾讯云主机后，能够在不暴露无鉴权管理台与 API 到公网的前提下，通过受控的访问边界安全地查看 `/admin/` 管理台与调用 `/api/v1/**` 接口；未经授权的公网来源无法直接访问服务端口。

**Why this priority**: OryxOS 当前版本默认监听 `127.0.0.1:8080` 且无内置登录认证与 RBAC，若直接监听 `0.0.0.0` 并放行公网端口，会导致管理台、会话历史、工具执行与手动恢复接口完全裸露，是上线前的最高优先级安全阻断项。

**Independent Test**: 服务在云主机启动后，从外部公网尝试直连服务器 `8080` 端口应被拒绝或不可达；通过既定的受控访问方式（待确认）访问 `/admin/` 与 `/api/v1/health` 应正常返回且可完成同源管理台操作。

**Acceptance Scenarios**:

1. **Given** OryxOS 已在腾讯云主机运行，**When** 任意未授权公网客户端直接请求服务器公网 IP 的 `8080` 端口，**Then** 连接被拒绝或超时，无法访问 `/admin/` 或任何 `/api/v1/**` 接口。
2. **Given** 运维人员使用已配置的受控访问方式连接管理台，**When** 打开 `/admin/` 并查询健康状态、Agent 列表与运行状态，**Then** 页面正常加载且同源接口返回有效数据。
3. **Given** 部署配置与发布脚本已提交至 Git 仓库，**When** 审计仓库内所有受跟踪文件，**Then** 不包含任何真实公网 IP（若需脱敏）、SSH 私钥/密码、模型 API Key 或通知 Webhook URL。

### User Story 2 - 持久化工作区、服务常驻与数据备份 (Priority: P1)

服务以系统守护进程方式常驻运行并支持开机自启；程序发布包与运行工作区（数据库、Agent 定义、长期记忆、输出目录、密钥文件、运行日志）严格分离，且存在可验证的定期备份与恢复机制，确保云主机重启或异常退出后服务自动恢复且历史数据不丢失。

**Why this priority**: 生产环境若将工作区与发布包混放或未配置守护进程与备份，不仅在版本升级时极易误删 SQLite 数据与密钥，也无法保证主机重启后的可用性与审计可恢复性。

**Independent Test**: 模拟云主机重启或服务进程异常终止，验证服务在无人干预下自动拉起并恢复历史会话与调度状态；执行备份与恢复演练，验证恢复后的工作区可通过只读检查与健康探测。

**Acceptance Scenarios**:

1. **Given** 服务已在云主机正常运行并产生至少一条会话与审计记录，**When** 触发服务器重启或强制终止服务进程，**Then** 守护进程管理机制在规定时间内自动重新启动服务，且重启后可查询到之前的会话与执行历史。
2. **Given** 云主机上存在独立的工作区目录与程序安装目录，**When** 检查目录结构与文件权限，**Then** 程序包目录不包含业务数据或密钥，工作区内的本地密钥文件权限为仅属主可读写（`0600`），且同一工作区同时仅允许一个重型服务实例运行。
3. **Given** 备份策略已启用，**When** 执行一次备份并模拟工作区数据库损坏后从备份还原，**Then** 还原后的数据库结构完整、无锁冲突，服务可正常启动并通过健康检查。

### User Story 3 - 基于 GitHub Actions 的平滑发布与快速回滚 (Priority: P2)

代码推送至指定分支或手动触发工作流后，由 GitHub Actions 自动完成构建、回归校验与产物打包，并通过受控 SSH 通道将新版本程序包推送至腾讯云主机、切换运行版本并重启生效；当新版本启动失败或健康检查不通过时，能够在短时间内自动或人工回滚到上一个已知可用版本，且不破坏现有工作区数据。

**Why this priority**: 单机服务每次更新需要停旧启新（受单工作区文件锁约束），通过 GitHub Actions 统一执行构建门禁、产物校验、远程切换与健康探测，可避免手工操作失误与服务器本地编译的资源开销。

**Independent Test**: 触发一次 GitHub Actions 工作流将版本 A 升级到版本 B，验证服务成功切换并保留工作区数据；再模拟一个无法通过健康检查的坏版本，验证可回滚至版本 A 并恢复服务。

**Acceptance Scenarios**:

1. **Given** 云主机正在运行版本 A，**When** 运维人员执行发布流程部署版本 B，**Then** 流程先停止旧实例释放工作区锁，切换新版本程序包并启动服务，随后健康检查确认服务就绪。
2. **Given** 版本 B 启动失败或健康检查超时未通过，**When** 执行回滚流程，**Then** 服务切回版本 A 对应的程序包并重新拉起，工作区数据库、记忆与配置保持完整未受损。

---

### User Story 4 - 外部模型与通知定时任务云端联调 (Priority: P3)

在访问边界与常驻运维就绪的基础上，按确认范围决定是否将外部模型（如 DeepSeek）与通知通道（如飞书 Webhook）及相关定时任务（如每日天气推送）迁入云端工作区并完成真实链路验证。

**Why this priority**: 真实外部凭证联调属于业务扩展验证，必须建立在 P1 安全边界与密钥隔离机制就位之后，避免在安全未闭环前将真实 API Key 与 Webhook 放入云端环境。

**Independent Test**: 在配置受控的云端密钥与启用的定时任务后，通过管理台或接口手动触发一次任务执行，验证外部模型响应与通知送达，并确认执行记录与脱敏审计落库。

**Acceptance Scenarios**:

1. **Given** 云端工作区已通过 `0600` 本地密钥文件配置有效的模型与通知凭证，**When** 手动触发一次定时任务（或到达预定调度时间），**Then** 任务成功调用外部模型并将结果推送至目标通知渠道，同时管理台可查到对应执行记录。
2. **Given** 日志与持久化审计记录已生成，**When** 检查输出日志与执行详情，**Then** 所有模型 API Key、Webhook URL 等敏感字段均未明文泄露。

---

### Edge Cases

- **工作区文件锁残留或冲突**：若旧进程异常僵死未及时退出导致工作区锁占用（退出码 `4` / `WORKSPACE_BUSY`），发布与重启流程如何确保旧进程彻底停止后再启动新实例，避免反复重启失败。
- **磁盘空间不足或日志膨胀**：SQLite WAL 文件、应用运行日志或历史发布包/备份长期累积耗尽云主机磁盘时，如何通过日志轮转与备份/旧包保留数量上限防止服务写入失败。
- **关键持久化失败触发安全暂停（`PAUSED_RECORDING`）**：当云主机磁盘异常或存储写入失败导致运行时进入 `PAUSED_RECORDING`（`HTTP 503`）时，健康监控与运维人员如何识别该状态并在排查后通过管理台或恢复接口人工恢复，而非盲目自动重启掩盖数据问题。
- **公网高危探测与暴力请求**：当采用公网反向代理暴露入口时，如何限制异常高频请求与扫描探测对单机有限内存/CPU 资源的耗尽。
- **Java 内存与低配云主机资源竞争**：若云主机内存较小（例如 2GB），如何合理控制服务堆内存与系统、反向代理、SQLite 页缓存之间的内存分配，避免发生 OOM Kill。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 (安全访问边界)**: 部署方案 MUST 确保 OryxOS 默认仅绑定回环地址（`127.0.0.1:8080`），不得直接向公网放行无鉴权的 `8080` 端口；公网访问 MUST 采用“已备案域名（`curlyhair.cn` 及其子域名）+ HTTPS + Basic Auth 反向代理（通过服务器现有宝塔面板 Nginx 托管）”方式，所有未通过认证的请求均不得穿透至 `127.0.0.1:8080`（具体子域名或子路径挂载方式在 `plan` 阶段确认）。
- **FR-002 (敏感信息零入库)**: 仓库内所有受 Git 跟踪的文件（包括规格、方案、脚本、配置模板、文档）MUST NOT 包含真实服务器公网 IP（当用户要求脱敏时）、SSH 私钥/密码、模型 API Key 或通知 Webhook URL；所有敏感凭证 MUST 仅存在于本地隔离环境或云主机权限为 `0600` 的受控密钥文件中。
- **FR-003 (运行环境与进程托管)**: 云主机 MUST 具备符合项目基线的运行环境（Java 21），并将 OryxOS 服务注册为系统级守护进程，支持开机自启、异常退出自动重启以及受控的优雅停机。
- **FR-004 (目录与权限隔离)**: 云主机上的程序包目录、工作区数据目录、日志目录与备份目录 MUST 彼此分离；程序版本更新不得覆盖或清空工作区内的 `oryxos.db`、Agent 定义、长期记忆、输出文件与本地密钥；工作区目录与密钥文件 MUST 使用最小权限原则（非 root 专用运行用户或受限属主权限，密钥文件为 `0600`）。
- **FR-005 (可观测性与日志管理)**: 服务运行日志（标准输出/应用日志）MUST 持久落盘并配置自动轮转与保留策略，避免单文件无限增长占满磁盘；日志中不得明文打印密钥或完整敏感凭证。
- **FR-006 (数据备份与恢复)**: 系统 MUST 提供针对工作区核心状态（含一致性 SQLite 数据库快照、`runtime.yaml`、`agents/` 与 `memory/`）的定期备份机制与可验证的恢复操作指引，确保在单机故障或误操作后可还原至最近可用状态。
- **FR-007 (GitHub Actions 安全发布与版本回滚)**: 发布流程 MUST 由 GitHub Actions 工作流驱动（支持分支推送与手动触发，具备并发控制），在构建端完成编译与回归门禁及校验摘要生成后，通过 GitHub Secrets 注入的 SSH 凭证将产物推送至云主机版本目录、停旧启新（避免工作区锁冲突）、执行本机健康探针，并保留历史可用版本以支持快速回滚；工作流结束后 MUST 清理构建机临时密钥文件。
- **FR-008 (目标主机基线与资源约束)**: 部署方案 MUST 适配目标腾讯云 CVM 主机基线：北京三区标准型 S4（2核 4GiB、3Mbps 带宽、Linux x86_64 / CentOS 系，已部署宝塔面板），合理控制 JVM 堆内存上限以与宝塔 Nginx 及同机现有服务共存，并通过 GitHub Secrets 维护的 SSH 密钥对（推荐密钥认证，不使用明文密码）完成自动化免密发布（所有真实 IP 与主机标识均脱敏，不入库）。
- **FR-009 (云端外部能力迁移范围)**: 本次部署 MUST 同步迁移并启用外部模型（DeepSeek）与飞书 Webhook 通知定时任务（如每日天气推送）；相关 API Key 与 Webhook URL MUST 仅通过 GitHub Secrets 注入云主机工作区 `0600` 权限的 `secrets.local.yaml`，并在部署验收阶段完成真实端到端触发与脱敏审计落库验证。
- **FR-010 (运维文档与验收可重复)**: 部署方案完成后，仓库内 MUST 产出与实际部署一致脱敏的运维与故障排查指引（覆盖启动、停止、状态查看、日志排查、备份还原、`PAUSED_RECORDING` 人工恢复及回滚步骤）。

### Key Entities

- **云端发布包 (Release Artifact)**: 经本地构建与回归验证通过的可执行单机程序包及其校验摘要与版本标识，部署于独立的版本目录中用于切换与回滚。
- **云端工作区 (Cloud Workspace)**: 与程序包分离的持久化状态根目录，包含工作区配置、Agent 定义、SQLite 数据库及 WAL 文件、长期记忆、受控输出与进程文件锁。
- **受控密钥配置 (Secret Configuration)**: 仅存储于云主机本地受限权限（`0600`）文件中的外部模型凭证、通知 Webhook 或反向代理认证凭据，不进入版本控制系统。
- **备份快照 (Backup Snapshot)**: 在保证数据库一致性前提下生成的历史工作区归档副本，包含时间戳标识与保留周期策略。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001 (公网暴露面零裸露)**: 在云主机服务运行状态下，从非授权外部网络直接探测服务内部监听端口（`8080`）的成功率为 `0%`；仅经由已选定的受控访问方式可 `100%` 访问管理台与健康接口。
- **SC-002 (自愈与重启恢复)**: 触发云主机重启或强制结束服务进程后，服务在 `60 秒` 内自动恢复为可用状态，且重启前已落库的会话、记忆与定时任务状态 `100%` 完整保留。
- **SC-003 (发布与回滚时效)**: 正常版本发布从上传程序包到新版本通过健康检查的总耗时不超过 `5 分钟`；当模拟新版本启动失败时，回滚至上一可用版本并恢复服务可用性的耗时不超过 `3 分钟`，且工作区数据零丢失。
- **SC-004 (敏感信息零泄露)**: 针对仓库全量受跟踪文件执行敏感信息扫描，真实公网 IP（按脱敏要求）、SSH 凭证、模型 API Key 与通知 Webhook URL 的命中数为 `0`。
- **SC-005 (备份可恢复性)**: 至少完成 `1 次` 端到端备份与模拟还原演练，还原后的服务可正常启动且健康检查与历史数据查询通过率 `100%`。

## Assumptions

- OryxOS 当前仍以单机内核形态运行（单节点 SQLite WAL + 单工作区进程互斥锁），本次部署不引入多节点集群、分布式存储或应用内置多租户改造。
- 本地开发环境已完成仓库构建与本地回归基线（`./tools/dev/mvnw -B -ntp verify`），云主机侧主要承担运行时托管而非从源码编译。
- 云主机具备稳定的基础网络出口，若启用外部模型或通知服务，可正常发起出站 HTTPS 请求。
- 本规格遵循项目宪章（`Constitution v1.0.0`）原则 IV（工具操作受控与凭证边界）与原则 VI（每个用户故事可演示、可检查），具体实现方案（如选用的反向代理组件、备份脚本细节、JVM 内存参数）将在后续 `speckit-plan` 阶段细化。
