## 背景与现状（规格输入）

本规格只覆盖五大核心能力中的 **Provider**，是一次**不改变外部行为**的结构重构。输入是第 16 节课件
（`/Users/jianghaoran/jikeshijian/oryxos/docs/class/第16节：Agent Provider 原理解析、实现与代码讲解.md`，仓库外文件）
与 2026-11-23 当前检出的 `oryxos-provider`、`oryxos-core` 代码。课件是教学示意，凡与已确认的
spec 001 / plan 001 冲突处，以后者为准（见下方“保留的偏差”）。

### 课件原则与当前代码对照

| 课件要求 | 当前实现 | 结论 |
| --- | --- | --- |
| 职责划窄：只挑模型、调一次、拿结果 | `SpringAiProvider` 只做一次低层同步请求，无重试、无 fallback | 已满足 |
| 坑一：provider 名字 → 调用实例显式映射，不靠类型扫描 | `ProviderRegistry` 按 `runtime.yaml` 逐条建表，未知名明确失败，单个 provider 配置错误只影响引用它的 Agent | 已满足 |
| 坑二：关闭框架自动工具执行 | 直接使用协议层低层客户端，根本不经过框架的对话模型与工具回调机制 | 已满足，但**没有防回退的结构性守护**，只有行为测试 |
| 坑三：先确认依赖可解析 | 父 POM 锁定 Spring AI BOM 1.1.8，仅引入 OpenAI 兼容协议包 | 已满足 |
| 成功与失败都审计 | `AuditedProvider` 先记“开始”，再记“成功/失败”；记录失败不会被当作成功或自动重放 | 已满足（比课件更严格） |
| 核心类名 `ProviderService` | 实际入口类名为 `ProviderRegistry`；技术方案 §1、§10 及课件均称 `ProviderService` | **命名偏差，需重构** |
| 一次调用一条清晰路径 | 一次模型调用被 ReAct 循环、审计包装层、协议适配层**三次重复申请运行准入**；请求合法性也在入口与适配层**校验两次** | **结构冗余，需重构** |
| 测试按验收点组织（路由 / 工具翻译 / 审计） | 绝大部分 Provider 验收点集中在一个约 1000 行的契约测试类中，难以按课件的“每个坑一个回归测试”定位 | **可定位性不足，需重构** |
| 工具格式适配器只翻译不执行 | 翻译逻辑位于请求选项映射中；另有一个仅被测试引用、只做转发的工具名映射包装类 | 翻译已满足；**转发包装类为死代码，需清理** |

### 重复准入的实际后果

运行准入的设计语义是“准入即交接边界，已准入的动作持续在途直到真正退出”。当前三层重复准入带来两个可观察问题：

1. 一次模型调用期间，工作区“在途动作数”记为 3 而不是 1，任何依赖该计数的暂停/观测判断都被放大。
2. 外层已准入、审计已写“开始”之后，若执行恰好被停止或工作区暂停，内层准入会拒绝，审计留下一条
   **“失败”但实际上从未向模型服务发出请求**的记录，与“已准入动作持续到退出”的语义矛盾。

### 保留的偏差（不按课件改动）

| 课件写法 | 保留的已确认依据 |
| --- | --- |
| 独立 `.oryxos/profiles/*.yaml` + `ProfileLoader` | Agent 唯一定义源是 `agents/<name>/AGENT.md` frontmatter（spec 001 FR-002） |
| provider 全局层写在 `application.yaml` | `runtime.yaml` 是权威配置，重启加载（spec 001 FR-003、plan 已确认决定） |
| 温度由每个 Agent 的 Profile 决定 | 温度等协议选项属于 provider 定义；Kimi 禁止发送 temperature（contracts/configuration.md） |
| `chat(sessionId, Profile, Prompt)` 签名 | 审计按执行（execution）关联，执行再关联会话；入参为单一请求对象 |
| `llm_calls.success` / `error_message` 列 | 使用 `status`（开始/成功/失败）与 `error_code`；不落原始错误文本，避免泄露凭证与响应体 |
| 依赖 Spring AI Alibaba 的对话模型抽象 | plan 001 选用低层单次调用以保留供应商协议字段（reasoning_content、thinking 等） |

## Clarifications

### Session 2026-11-23

- Q: 模型调用已放行且审计已记“开始”后，执行被停止或暂停，这次调用该怎么处理？ → A: 继续跑完，按真实结果记审计；停止从下一次放行开始生效；不新增审计状态，单次调用仍受剩余时间预算约束。
- Q: 改名只限对外入口，还是内部部件一起改？ → A: 只把 `ProviderRegistry` 改为 `ProviderService`；审计包装层 `AuditedProvider`、协议适配层 `SpringAiProvider` 保持原名。
- Q: 本次改动到的 provider 文件在质量基线里的存量违规怎么处理？ → A: 全部修掉并删除对应基线条目；基线总数只减不增。
- Q: 拆分 Provider 契约测试时，原测试方法名保留还是改为课件式中文名？ → A: 方法名一律保留，只迁到专项类；同步更新测试分组登记与用例计数，新增的在途计数测试与结构守护测试登记进 `us1-contract`。
- Q: 仓库外第 16 节课件与已确认设计不一致之处，这次怎么处理？ → A: 不改课件原文；在本规格目录新增课件修订建议文档，逐处列出课件旧写法、重构后现行写法与依据。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一次模型调用只有一个准入和一次校验 (Priority: P1)

运维或开发者观察运行中的执行时，一次模型调用在工作区里只算作一个在途动作；已经准入并开始审计的模型调用，
不会因为准入之后发生的停止或暂停，在审计里留下一条“失败但从未发出请求”的记录。非法请求（空任务、无剩余时间、
未知 provider）仍然在发出任何网络请求、写任何审计之前被拒绝。

**Why this priority**: 这是唯一带有可观察行为偏差的问题，直接影响审计可信度与暂停判断，属于“可审计”卖点的正确性。

**Independent Test**: 使用可控假模型服务，让一次调用在服务端阻塞；阻塞期间读取工作区在途动作数，应为 1。
在外层准入完成后、请求发出前停止执行，该次调用应完整结束并按实际结果记录，而不是记成失败。

**Acceptance Scenarios**:

1. **Given** 一个正在等待模型响应的执行，**When** 读取工作区在途动作数，**Then** 该次模型调用只贡献 1。
2. **Given** 模型调用已被 ReAct 循环准入、审计已写“开始”，**When** 执行随后被停止，**Then** 本次调用继续到真正退出，
   审计终态反映实际结果（成功或模型服务侧失败），不出现“执行已停止”类失败码；停止在下一次准入时生效。
3. **Given** 执行在模型调用准入**之前**已被停止，**When** ReAct 循环尝试发起模型调用，**Then** 调用被拒绝，
   不发出网络请求、不写“开始”审计（与现状一致）。
4. **Given** 空任务、剩余时间为零或未知 provider 名，**When** 发起调用，**Then** 返回与现状相同的错误码，
   不发出网络请求、不写审计；请求合法性只在 provider 入口校验一次。

---

### User Story 2 - 课件与技术方案中的概念能在代码里一一找到 (Priority: P1)

学员或新贡献者读完第 16 节课件和技术方案后，可以按名字直接找到 Provider 入口、工具翻译、审计包装三个部件，
不需要猜测 `ProviderRegistry` 就是 `ProviderService`；模块里不再有只被测试引用的转发类。

**Why this priority**: 本项目以课件驱动开发，命名对不上会让每节课的“代码讲解”都多一层翻译，后续 ReAct、
定时等课件都引用 `ProviderService`。

**Independent Test**: 在仓库中按课件与技术方案的名字搜索，能命中唯一的 Provider 入口；全仓库搜索不到旧入口名
（历史证据与已归档文档除外）；被删除的转发类在主代码与测试中均无引用。

**Acceptance Scenarios**:

1. **Given** 重构后的检出，**When** 搜索 `ProviderService`，**Then** 命中 provider 模块唯一的对外入口，
   启动装配通过它向 ReAct 循环提供模型调用能力。
2. **Given** 重构后的检出，**When** 搜索只做转发的工具名映射包装类，**Then** 主代码与测试中均无引用，
   原先依赖它的测试直接使用核心工具名映射。
3. **Given** 规格“课件原则与当前代码对照”表，**When** 逐行在代码中查找对应部件，**Then** 每一行都能定位到具体类。

---

### User Story 3 - 课件点名的每个坑都有独立可定位的回归测试 (Priority: P2)

维护者改动 Provider 后，如果破坏了“显式按名路由”“不自动执行工具”“失败也审计”任意一条，
会有一个名字直接说明该约束的测试变红，而不是在一个千行测试类里定位。并且新增一个结构性守护：
provider 模块一旦引入框架的对话模型或自动工具回调机制，构建即失败。

**Why this priority**: 行为已经被现有测试覆盖，这一条提升的是可维护性和课件“把坑钉死”的教学对应，不改变运行行为。

**Independent Test**: 分别故意破坏三条约束（让路由取错实例、在 provider 模块引用框架对话模型、跳过失败审计），
每次对应的专项测试类都失败，且失败信息指明约束名称。

**Acceptance Scenarios**:

1. **Given** 两个 provider 同时配置，**When** Agent 按名引用其中一个，**Then** 路由专项测试验证另一个服务收到的请求数为零。
2. **Given** provider 模块源码或依赖中出现框架对话模型、工具回调管理器等自动执行机制，**When** 执行测试，**Then** 守护测试失败。
3. **Given** 模型服务超时或拒绝，**When** 调用失败，**Then** 审计专项测试验证错误继续抛给上层，且先落下一条终态为失败、
   带分类错误码的记录。
4. **Given** 拆分前后的测试集，**When** 对比测试方法名清单，**Then** 原契约测试的每个方法名都在拆分后的某个专项类中原样存在，
   数量不减少；按既有分组命令（如 `us1-contract`、`kernel-provider-timing`）运行时，测试报告核对通过且用例数等于登记数。

### Edge Cases

- 记录“开始”审计失败时：仍然不发出请求，返回“无法记录模型意图”类错误（现状保留）。
- 请求已发出、终态审计写入失败时：仍然返回“部分记录失败、禁止自动重放”类错误，不把调用当作成功（现状保留）。
- `ProviderService` 关闭后再调用：仍明确返回 provider 不可用，不访问已释放的连接。
- 同一执行内跨 provider/model 续接推理内容：仍拒绝并提示新建会话（现状保留）。
- 未经 ReAct 循环、直接调用 provider 入口的测试或工具（不带运行准入句柄）：仍可正常完成单次调用。
- 计时观测（transport / reply 分段）在去掉内层准入后仍按原分段名输出，不丢段。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：一次模型调用在运行准入层面只被申请一次，申请点位于 ReAct 循环（调用方）；审计包装层与协议适配层不再重复申请。
- **FR-002**：已准入的模型调用必须持续到真正退出；准入之后发生的停止、暂停或截止，只影响下一次准入，
  不得让当前调用以“执行已停止 / 已暂停”记为失败；不主动中断在途网络请求，不新增审计状态值。
  在途调用的最长时长仍由请求携带的剩余时间预算限定，超出即按现有超时错误码结束。
- **FR-003**：provider 层按 FR-001 不再使用运行准入句柄，因此从模型请求对象中移除该句柄，避免调用方误以为 provider 负责准入；
  移除后 ReAct 循环、上下文组装与所有测试保持编译与行为一致。
- **FR-004**：请求合法性（模型名、迭代序号、末条用户消息非空、剩余时间为正）只在 provider 入口校验一次，
  且校验发生在写任何审计、发出任何网络请求之前；协议适配层只保留“路由与自身定义一致”的防御检查。
- **FR-005**：模型服务异常到分类错误码的映射在一次调用中只执行一次；对外错误码集合与现状完全一致。
- **FR-006**：provider 模块对外入口命名为 `ProviderService`，与技术方案 §1、§10 及第 16 节课件一致；
  启动装配、测试与仓库内现行文档同步更新，历史证据文件不改写。改名只涉及这一个类；
  `AuditedProvider`、`SpringAiProvider` 及其余 provider 内部类保持原名。
- **FR-007**：删除仅被测试引用、只做转发的工具名映射包装类；依赖它的测试改用核心层工具名映射。
- **FR-008**：Provider 测试按验收点拆分为独立测试类，至少包括：按名路由、配置隔离与入口校验，工具 schema 翻译与名字映射，
  审计与错误分类（成功/失败/记录失败），协议与时间预算，传输与计时；原有测试场景一个不少，分组标签保持可被既有命令选中。
  原测试方法名一律保留不改，只迁移所在类；测试分组登记文件（`tools/dev/test-groups.json`）、开发入口说明中的用例计数
  与 spec 001 verification 的分组表同步更新为新类名。FR-001/FR-002 的在途计数测试、FR-004 的非法请求零审计测试与 FR-009 的结构守护测试
  登记进 `us1-contract` 分组，计入默认本地回归。
- **FR-009**：新增结构性守护测试：provider 模块不得引用框架的对话模型、对话客户端或自动工具回调/执行机制；
  违反时测试失败并指明约束。
- **FR-010**：重构不得改变任何外部可观察契约：HTTP 接口与 OpenAPI 文档、CLI 输出与退出码、`runtime.yaml` 配置格式、
  `llm_calls` 表结构与写入内容（除 FR-002 修正的误记失败外）、日志字段、错误码集合。
- **FR-011**：不新增数据库迁移脚本，不引入新依赖，不新增 fallback、重试、熔断等课件明确延后的能力。
- **FR-012**：本次新增、改名或修改的 provider 模块主代码文件，必须清除其在质量基线中登记的全部存量违规，
  并从基线删除对应条目；基线中不得出现指向已不存在文件的条目，基线总条目数只减不增。
- **FR-013**：在本规格目录交付一份第 16 节课件修订建议，覆盖“保留的偏差”表全部条目及本次改名（`ProviderService`），
  每条给出课件原写法、重构后的现行写法、对应代码位置与依据（spec 001 条款或本规格 FR）；仓库外课件原文不修改。

### Key Entities

- **模型请求**：一次模型调用的输入，包含 provider 名、模型名、系统提示、有序消息、可用工具 schema、工具名映射、
  剩余时间、所属执行与迭代序号；重构后不再携带运行准入句柄（FR-003）。
- **模型调用审计记录**：每次调用一条，从“开始”到“成功/失败”，记录 provider、请求模型、实际模型、耗时、token 与分类错误码；结构不变。
- **Provider 入口（ProviderService）**：按名路由到已配置的协议适配实例，负责一次性请求校验并经审计包装层调用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：一次模型调用在途期间，工作区在途动作计数恰为 1（现状为 3），由自动化测试断言。
- **SC-002**：准入后停止执行的场景下，“开始后记为执行已停止的失败审计”出现次数为 0。
- **SC-003**：全量本地构建与测试（含格式、规约、安全门禁）通过；重构前后测试场景数不减少，失败数为 0。
- **SC-004**：按课件对照表逐行查找，9 行中标注需重构或需补守护的 5 行全部能定位到重构后的代码或守护测试，旧入口名在主代码与测试中出现次数为 0。
- **SC-005**：三类故意破坏（错路由、引入自动工具执行、跳过失败审计）各自必然让对应的专项测试类失败，且失败信息指明被破坏的约束；
  其它测试类是否连带失败不作要求（例如两 provider 演示测试 `ProviderSmokeTest` 在错路由时也会失败），但需如实记录。
- **SC-006**：HTTP 契约零差异测试与 CLI 集成测试结果与重构前一致。
- **SC-007**：质量基线中 provider 模块被改动文件的条目数降为 0，基线总条目数低于重构前。
