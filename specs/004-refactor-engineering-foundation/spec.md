**Feature Branch**: `004-refactor-engineering-foundation`

**Status**: Planned（plan/tasks 已生成，2026-11-21 完成一致性检查）

**Input**: User description: "咱们来重构咱们的初始化的代码吧。咱们先看下现在的架构代码，我已经部署到了服务器上。以 oryxos-init 的约束为主，重构咱们的代码。"

## 背景与现状（规格输入）

本规格针对的是 **工程地基**（`oryxos-init` skill 定义的范围），不是五大核心能力的业务行为。
现状核对于 2026-11-21 完成，依据是当前检出的构建文件、启动配置与部署脚本，不是历史文档描述：

| `oryxos-init` 检查项 | 当前状态 | 本次定位 |
| --- | --- | --- |
| 9 个 Maven 模块 + 可执行 fat JAR | 已具备；父 POM 锁定 Spring Boot 3.5.16、JDK 21，enforcer 校验 JDK/Maven 版本 | 保留，不重建 |
| HTTP 服务 + 虚拟线程 | 已具备；默认回环监听 `127.0.0.1:8080` | 保留 |
| 统一响应体 + 全局异常处理 + OpenAPI | 已具备 `code/message/data/timestamp/traceId` 信封、错误码到 HTTP 状态映射、已发布 OpenAPI 契约（19 操作 / 44 schema 零差异测试） | 保留公开契约，仅补齐与日志关联 |
| 敏感配置 `${ENV_VAR}` 占位 | 已具备；云端密钥走 `0600` 本地文件 | 保留 |
| 结构化日志 | **缺失**：仅 stderr 文本输出，无生产 JSON 格式，无请求级追踪标识写入日志；响应里的 `traceId` 是随机值，不能用来在日志中检索同一请求 | 本次补齐 |
| 健康/指标暴露（Actuator + Prometheus） | **缺失**：健康检查依赖自定义 `/api/v1/health`，发布脚本与管理台均使用该端点；无运行时指标 | 本次补齐，且不替换现有端点 |
| 服务器日志持久化 | **缺失**：日志只进 journald，未开启持久化（CentOS 默认重启丢失）；`/var/log/oryxos` 已创建但无写入 | 本次补齐（FR-001a） |
| 服务器监控栈 | **缺失**：服务器上无指标采集与看板 | 本次新增 Prometheus + Grafana（FR-007a） |
| 服务器侧配置随发布同步 | **缺失**：systemd 单元仅在首次初始化时安装，发布只替换 JAR 与工作区配置 | 本次补齐（FR-020a） |
| 代码格式（Google）+ 编码规约（阿里 P3C）+ Checkstyle + `.editorconfig` | **缺失**：无任何格式或规约检查；大部分源码为 2 空格缩进，个别文件（如薄 CLI 入口）为 4 空格 | 本次补齐 |
| 代码安全扫描（SpotBugs + Find Security Bugs + PMD + 依赖 CVE） | **缺失** | 本次补齐 |
| CI + pre-commit 强制执行 | **部分**：仅有"push main → 构建回归 → 部署腾讯云"工作流，无独立的合并前检查，无本地提交前检查 | 本次补齐 |

已部署到腾讯云单机（`specs/002-tencent-cloud-deployment`）的发布链、systemd 单元、nginx 反向代理与自动回滚是本次改动的 **外部约束**：任何改动不得使现有发布流程、健康探针与回滚失效。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 开发者本地一条命令复现全部质量门禁 (Priority: P1)

开发者在个人机器上，通过项目既有的统一构建入口（`tools/dev`）执行一次完整校验，即可同时得到：代码格式是否符合 Google 风格、是否违反阿里编码规约、是否存在静态安全缺陷、所有既有测试是否通过。格式问题可以一条命令自动修复；规约与安全问题给出文件、行号与规则说明。

**Why this priority**: 没有本地可复现的门禁，CI 阻断只会变成"推送后才知道失败"，开发者会倾向于绕过检查。本地与 CI 使用同一套规则、同一条命令，是其余所有门禁生效的前提。

**Independent Test**: 在干净检出上执行统一校验命令应全部通过；随后故意写入一处格式错误、一处规约违规（如捕获异常后不处理）、一处静态安全缺陷（如拼接 Shell 命令），再次执行应分别被对应检查拦截并定位到行；执行自动格式化后格式错误消失，其余两项仍被拦截。

**Acceptance Scenarios**:

1. **Given** 干净检出且已完成本次重构，**When** 开发者执行统一完整校验命令，**Then** 格式检查、编码规约检查、静态安全扫描与全部既有本地测试均通过，且总耗时在可接受范围内（见 SC-001）。
2. **Given** 某 Java 文件缩进/导入顺序不符合 Google 风格，**When** 执行校验，**Then** 构建失败并列出不合规文件；**When** 执行自动格式化命令，**Then** 该文件被修正且再次校验通过。
3. **Given** 本次重构之后新增或修改的代码违反阿里编码规约的阻断级规则，**When** 执行校验，**Then** 构建失败并输出规则名称、文件与行号；**Given** 违规所在文件与规则类别已登记在存量基线中，**Then** 以报告形式输出、不阻断构建；**Given** 某次提交使基线条目数增加，**Then** 持续集成失败。
4. **Given** 新增代码存在 Find Security Bugs 可识别的高危模式（如路径穿越、命令注入、不安全反序列化），**When** 执行校验，**Then** 构建失败并指出缺陷类别与位置。
5. **Given** 开发者使用既有 `tools/dev/mvnw` 入口与既有测试报告门禁，**When** 新增的检查接入构建生命周期，**Then** 既有"禁止跳过测试、按分组核对报告"的约束仍然成立，新检查不能被该入口的参数绕过。

### User Story 2 - 运维在已部署服务器上获得结构化日志与可观测端点 (Priority: P1)

运维人员在腾讯云主机上查看服务日志时，每条记录都是结构化的（单行 JSON），携带时间、级别、线程、记录器、请求追踪标识和消息；当某个 HTTP 请求出错时，响应体中的 `traceId` 能直接在日志中检索到该请求的全部日志行。运维还可以在本机（回环地址）访问标准化的健康探针与指标端点，拿到 JVM、HTTP 请求、线程等运行指标。本地开发时日志保持易读的彩色文本。

**Why this priority**: 服务已在生产运行，当前出问题只能肉眼翻纯文本日志且无法按请求关联；没有指标就无法判断内存、请求延迟和线程状况，这是运维最直接的痛点。

**Independent Test**: 分别以开发与生产两种运行方式启动服务：开发方式下控制台为彩色文本；生产方式下每行输出均可被 JSON 解析且包含约定字段。向业务接口发起一个会失败的请求，取响应 `traceId` 在日志中检索，应命中该请求的日志行。请求健康与指标端点应返回 UP 与指标文本。

**Acceptance Scenarios**:

1. **Given** 以生产配置启动服务，**When** 读取服务输出的任意 100 行日志，**Then** 每一行都能被标准 JSON 解析，且包含时间戳、级别、记录器、线程、消息字段；在 HTTP 请求处理期间产生的日志行还包含追踪标识字段。
2. **Given** 一次 HTTP 请求返回了错误信封，**When** 用响应中的 `traceId` 在日志中检索，**Then** 能找到该请求对应的日志行，且不同请求的追踪标识互不相同。
3. **Given** 服务运行中，**When** 从服务器本机请求健康探针端点，**Then** 返回整体状态 UP，并可分别得到存活（liveness）与就绪（readiness）探针结果。
4. **Given** 服务运行中，**When** 从服务器本机请求指标端点，**Then** 返回 Prometheus 文本格式的指标，至少包含 JVM 内存、线程、GC、HTTP 请求计数/耗时，并带有 `application=oryxos` 标签。
5. **Given** 公网用户通过反向代理访问服务，**When** 请求健康/指标等运维端点，**Then** 不能在未通过访问控制的情况下读取到这些信息（与已有 OpenAPI 文档接口的公网屏蔽策略一致）。
6. **Given** 现有发布脚本与管理台依赖 `/api/v1/health`、`/api/v1/info`，**When** 新端点就位，**Then** 原端点行为与已发布 OpenAPI 契约保持零差异，发布脚本中的健康探针调用无需修改即可继续工作。
7. **Given** 任何日志级别或任何异常栈，**When** 日志中出现配置里的密钥、Webhook 地址等敏感值，**Then** 它们以脱敏形式呈现，与现有审计脱敏口径一致。
8. **Given** 服务器上已部署监控栈，**When** 运维人员经受保护入口打开 Grafana 看板，**Then** 能看到最近 24 小时的 JVM 与 HTTP 指标曲线；**When** 服务器重启后查看 `/var/log/oryxos/`，**Then** 重启前的 JSON 日志仍然存在，且目录总量不超过 1GB。

### User Story 3 - 合并与提交前自动强制执行门禁 (Priority: P2)

代码推送到任意分支或发起合并请求时，持续集成自动运行与本地完全一致的完整校验，任一检查失败即标红阻止合并；开发者本地提交时，提交前钩子先运行格式检查与快速静态检查，提前拦截最常见问题。已有的"push main → 部署"流程继续沿用同一校验，确保只有通过全部门禁的提交才会被部署到服务器。

**Why this priority**: 门禁只有被机器强制执行才有效。它依赖 US1 的规则集成形，因此排在其后；但在团队协作和 AI 生成代码的场景下，它是防止规范回退的主要手段。

**Independent Test**: 在一个分支上提交含格式错误的代码：本地钩子应拒绝提交；跳过钩子强行推送后，CI 应标红并指出失败步骤；修正后 CI 变绿。通过合并请求把一个通过门禁的提交合入 main，部署流程应完成发布并同步服务器侧配置；直接向受保护的 main 推送应被拒绝。

**Acceptance Scenarios**:

1. **Given** 已安装项目提供的提交前钩子，**When** 提交一处格式不合规的改动，**Then** 提交被拒绝并提示修复命令；修复后提交成功。
2. **Given** 推送或合并请求触发 CI，**When** 任一检查（格式、规约、静态安全、测试、依赖扫描策略见 US4）失败，**Then** 工作流失败且失败步骤名称清晰可辨；**When** 全部通过，**Then** 工作流成功。
3. **Given** 一个合并请求的完整校验与依赖漏洞扫描均通过并合入 main，**When** 部署工作流运行，**Then** 产物校验、远端切换、健康探针与自动回滚语义保持不变，并额外同步服务器侧监控配置与 systemd drop-in（FR-020a）；**Given** 门禁失败，**Then** 不进入部署步骤。
4. **Given** main 已开启分支保护，**When** 有人直接推送到 main 或合并未通过必过检查的请求，**Then** 平台拒绝该操作。
5. **Given** 提交前钩子的安装，**When** 开发者按文档执行一次安装命令，**Then** 不需要安装任何全局软件，也不修改仓库之外的环境。

### User Story 4 - 第三方依赖已知漏洞持续扫描 (Priority: P2)

维护者能够知道当前依赖树中是否存在已公开披露的高危漏洞（按 CVSS 阈值），并在超过阈值时得到明确失败与依赖坐标、漏洞编号的报告，以便决定升级或登记例外。扫描作为独立的持续集成作业在合并请求与每日定时运行，超阈值阻断合并但不进入默认校验、不阻断部署，避免因外部漏洞库不可用导致日常构建或部署随机失败。

**Why this priority**: 项目直接面向外部模型与通知服务，依赖面较广；但漏洞库下载依赖外网且耗时，若放在每次构建中会显著影响体验并可能拖垮发布，因此需要单独设计。

**Independent Test**: 在隔离分支临时引入一个带有已知高危 CVE 的旧依赖，触发扫描应失败并列出该依赖与 CVE；移除后扫描通过。漏洞库不可达时该作业失败并明确提示原因，部署工作流不受影响。

**Acceptance Scenarios**:

1. **Given** 依赖树中存在 CVSS ≥ 阈值的已知漏洞，**When** 运行依赖扫描，**Then** 结果为失败并列出依赖坐标、漏洞编号与评分。
2. **Given** 依赖树无超过阈值的漏洞，**When** 运行依赖扫描，**Then** 结果为通过并生成可查看的报告。
3. **Given** 已登记的例外（误报或已评估接受的漏洞），**When** 运行依赖扫描，**Then** 该条目被抑制且抑制文件中记录理由。

### User Story 5 - 工程基线可验证、可交接 (Priority: P3)

新加入的开发者或 AI 助手阅读一份简短的工程基线说明后，就能知道：有哪些门禁、如何本地运行、如何自动修复、如何查看日志与指标、CI 做了什么、遇到误报如何登记例外；并且这份说明的每一项都能在当前检出上实际执行验证。

**Why this priority**: 门禁与可观测性若没有说明和验证清单，很快会与实际配置漂移；但它依赖前四个故事的结果，因此最后交付。

**Independent Test**: 按说明逐条执行命令，每条命令的实际结果与说明一致；说明中没有引用不存在的文件或命令。

**Acceptance Scenarios**:

1. **Given** 工程基线说明已写入仓库文档，**When** 按其中命令顺序执行，**Then** 每条命令可运行且结果与描述一致。
2. **Given** `oryxos-init` 的 Definition of Done 清单，**When** 对照当前检出逐项核对，**Then** 每项有明确的"已满足 / 未满足及原因"记录。

### Edge Cases

- **存量代码规模**：约 300 个 Java 源文件从未经过格式与规约检查。一次性全量格式化会产生大范围纯格式 diff；阿里规约在存量代码上可能产生大量违规。已确认按 FR-014 处理：格式全量阻断，规约与安全只对新增/修改代码阻断，存量报告并逐步清零。
- **漏洞库不可达或限流**：CI 构建机或开发者网络无法下载漏洞数据时，已确认按 FR-017 处理：扫描拆为独立作业，失败只影响合并门禁，不影响默认校验与部署。
- **多入口日志语义**：CLI 轻命令（`init`/`status`/`--version`）把业务输出写到 stdout、诊断写到 stderr，这是既定契约，不是"日志"；结构化日志要求不能把 CLI 的 stdout 输出改成 JSON。
- **既有响应 `traceId`**：当前为每个响应生成随机值。改为与日志追踪标识一致后，响应字段名、类型与 OpenAPI 契约不能变化。
- **运维端点暴露面**：服务已通过公网反向代理暴露；新增的健康/指标端点若无访问控制会泄露运行信息，须与 OpenAPI 文档接口一样被屏蔽或受同一认证保护。
- **测试代码与生成代码**：测试代码是否纳入同等规约门禁？第三方生成或模板文件如何排除？需在规则配置中显式声明，避免"为过检查删测试"。
- **构建时长膨胀**：多项静态分析叠加可能使 `verify` 明显变慢；需要给出目标与测量方式，并允许把最慢的检查（依赖扫描）从默认生命周期中拆出。
- **低配服务器资源**：目标主机为 2 核 4GiB 并与 nginx 等共存；新增指标采集与 JSON 编码不得明显抬高常驻内存，JVM 堆上限设置保持不变；同机新增的 Prometheus 与 Grafana 受 SC-009 内存上限约束。
- **启动失败诊断**：`CONFIGURATION_ERROR`/`STORAGE_UNAVAILABLE` 等启动期诊断日志目前依赖 stderr 文本；切换到 JSON 后，发布脚本中 `journalctl` 的人工排障可读性应有说明（例如给出按级别与消息字段过滤的命令）。
- **日志目录或监控组件异常**：`/var/log/oryxos` 不可写或磁盘写满时，服务按 FR-001a 继续运行并告警；Prometheus 或 Grafana 未运行、配置同步失败时，不得影响 OryxOS 主服务的发布判定与回滚（FR-020a）。
- **监控数据增长**：Prometheus 数据目录按 15 天保留期自动清理，不得随时间无限增长。

## Requirements *(mandatory)*

### Functional Requirements

**结构化日志**

- **FR-001**: 系统 MUST 提供两种日志输出形态：开发形态为带颜色的可读文本；生产形态为每行一条、可被标准 JSON 解析的记录，包含时间戳、级别、记录器、线程、消息，以及异常栈（存在时）。形态由运行配置（profile）选择，部署到服务器的运行方式默认使用生产形态。
- **FR-001a**: 生产形态下，服务 MUST 在继续输出到标准错误流（进入 systemd journal）的同时，将相同的 JSON 日志写入服务器日志目录 `/var/log/oryxos/` 下的文件，并按天及单文件大小滚动：单文件不超过 50MB、保留 14 天、日志目录总量不超过 1GB，超限时自动删除最旧文件。日志目录路径与上述限额 MUST 可通过配置覆盖；日志目录不可写时服务 MUST 继续运行并在标准错误流中给出明确告警，不得因此启动失败。开发形态不写文件。
- **FR-002**: 系统 MUST 为每个进入业务 HTTP 接口的请求分配唯一追踪标识，并在该请求处理期间（含虚拟线程上执行的业务逻辑）产生的所有日志行中带上该标识；响应信封中的 `traceId` MUST 与该标识相同。若请求头中携带了约定的上游追踪标识，则 MUST 沿用而非重新生成。
- **FR-003**: 定时任务触发与 CLI 触发的 Agent 执行 MUST 同样获得可在日志中检索的执行标识（复用现有执行 ID 即可），不要求与 HTTP 追踪标识同名。
- **FR-004**: 应用代码 MUST 通过统一日志门面记录日志，不得使用标准输出/错误流打印日志；CLI 命令的业务输出（stdout）与诊断输出（stderr）属于命令行契约，不受此限制，且 MUST 保持现有格式不变。
- **FR-005**: 日志中出现的密钥、Webhook 地址等敏感值 MUST 经过脱敏，口径与现有审计脱敏一致；脱敏 MUST 覆盖异常消息与结构化字段。

**健康与指标**

- **FR-006**: 系统 MUST 暴露标准化的健康探针端点，可区分整体健康、存活探针与就绪探针；就绪状态 MUST 反映运行时实际就绪（例如处于 `PAUSED_RECORDING` 或存储不可用时不得报告就绪），与现有 `/api/v1/health` 的判定一致。
- **FR-007**: 系统 MUST 暴露 Prometheus 文本格式的指标端点，至少包含 JVM 内存、GC、线程、HTTP 服务端请求计数与耗时、进程运行时长，并为全部指标附加 `application=oryxos` 标签。
- **FR-007a**: 服务器上 MUST 部署 Prometheus 与 Grafana：Prometheus 定期采集 OryxOS 指标端点，数据保留 15 天；Grafana 以 Prometheus 为数据源，提供至少一个覆盖 JVM 内存/GC/线程与 HTTP 请求量/耗时/错误率的看板，看板定义以文件形式纳入仓库。两者 MUST 只监听回环地址，经现有 nginx 的 HTTPS + Basic Auth 访问；Grafana 匿名访问与自助注册 MUST 关闭，管理员凭证 MUST 只存在于服务器受控文件中，不得入库。两者的内存占用合计 MUST 有上限配置（见 SC-009），不得挤占 OryxOS 现有堆配置。
- **FR-008**: 新增运维端点 MUST 默认仅监听与业务端点相同的回环地址；在现有公网反向代理配置中 MUST 增加对这些端点的屏蔽或与管理台相同的认证保护，并更新部署目录中的 nginx 参考配置。
- **FR-009**: 现有 `/api/v1/health`、`/api/v1/info` 及全部已发布 OpenAPI 操作与 schema MUST 保持零差异；运维端点不得出现在已发布的业务 OpenAPI 文档中。

**代码格式与编码规约**

- **FR-010**: 构建 MUST 包含 Google Java 风格的格式检查，并提供一条自动格式化命令；格式检查覆盖所有模块的主代码与测试代码。
- **FR-011**: 仓库根目录 MUST 提供编辑器通用配置（`.editorconfig`），与格式检查规则一致（缩进、换行、编码、行尾空白）。
- **FR-012**: 构建 MUST 包含基于阿里巴巴 Java 开发手册（P3C）的编码规约检查，至少启用编码规约、并发与异常处理三组规则；格式类规则与 Google 风格冲突时以 Google 格式为准并显式禁用冲突规则。
- **FR-013**: 构建 MUST 包含 Checkstyle（Google 检查集）作为格式层兜底，其严重级别与豁免范围 MUST 显式配置，不得与格式化工具产生互相矛盾的要求。
- **FR-014**: 存量代码处理策略（已确认）：格式检查 MUST 对全仓一次性格式化并立即全量阻断；编码规约（P3C/Checkstyle）与静态安全扫描 MUST 对本次重构合入之后新增或修改的代码阻断，对存量代码先以报告形式输出、不阻断构建。基线（存量快照或 ratchet 基准点）MUST 以仓库内文件或可追溯的 Git 基准登记，存量违规数量 MUST 在工程基线说明中记录并随清零进度更新；不得把存量违规登记为永久例外。判定粒度（已确认）为"文件 + 规则"：新文件中的任何违规、或某文件出现基线未登记的规则类别，均阻断；持续集成 MUST 校验基线条目数只减不增，新增基线条目即失败。已知局限（某文件已登记的规则类别内再新增同类违规不被拦截）MUST 写入工程基线说明。

**代码与依赖安全**

- **FR-015**: 构建 MUST 包含静态安全缺陷扫描（SpotBugs + Find Security Bugs），覆盖 OWASP Top 10 对应模式（注入、路径穿越、不安全反序列化、弱加密、XXE 等），对主代码阻断，阈值与豁免文件显式配置。
- **FR-016**: 系统 MUST 提供第三方依赖已知漏洞扫描，按 CVSS 阈值（默认 7.0）判定失败，支持带理由的抑制文件，并生成可查看的报告。
- **FR-017**: 依赖漏洞扫描执行位置（已确认）：MUST 从默认完整校验（本地 `verify` 与部署工作流）中拆出，作为独立的持续集成作业在合并请求与每日定时触发时运行；超过阈值时 MUST 阻断合并，MUST NOT 阻断 main 的部署工作流。本地 MUST 提供显式开启该扫描的命令（如 Maven profile），默认不运行。漏洞库不可达或限流时该作业失败并明确提示原因，不得静默通过；漏洞库 API 密钥通过 CI 密钥注入。
- **FR-018**: 所有扫描与检查的豁免、抑制与例外 MUST 以仓库内配置文件形式登记并附理由，不得以注释掉检查或关闭插件的方式绕过。

**持续集成与提交前检查**

- **FR-019**: 仓库 MUST 提供在任意分支推送与合并请求时运行的持续集成工作流，串行执行格式检查、Checkstyle、编码规约、静态安全扫描与全部本地测试，任一失败则工作流失败；步骤名称 MUST 与本地命令一一对应。
- **FR-019a**: 合入流程（已确认）：main 分支 MUST 只通过合并请求合入，并开启分支保护，将"完整校验"与"依赖漏洞扫描"两个持续集成检查设为必过项、禁止直接推送；合并后由现有部署工作流发布。分支保护属于代码托管平台设置，仓库内 MUST 提供逐步开启说明与必过检查的确切名称，开启与否以平台实际设置核验为准。
- **FR-020**: 现有部署工作流 MUST 复用同一套校验，仅在全部通过后进入产物打包与远端部署；原有部署步骤（产物提取、校验和、rsync、健康探针、自动回滚）的语义保持不变。
- **FR-020a**: 服务器侧组件落地方式（已确认）：Prometheus 与 Grafana 程序由可重复执行（幂等）的服务器初始化脚本安装一次；它们的配置、Grafana 看板与数据源定义、OryxOS 服务的 systemd drop-in（含生产日志形态所需环境变量）MUST 随仓库版本管理，并由发布流程在每次发布时同步到服务器、仅在内容变化时重载对应服务。同步失败 MUST 使本次发布失败并触发既有回滚，不得留下新旧混合配置；监控组件同步失败不得影响 OryxOS 主服务的回滚判定。nginx 规则仍在宝塔面板手工维护，仓库只更新参考片段与操作说明。
- **FR-021**: 仓库 MUST 提供提交前钩子及其安装命令：钩子执行格式检查（或自动格式化后暂存）与快速静态检查；安装不依赖全局软件，不修改仓库之外的环境；钩子可被显式跳过但 CI 仍会拦截。
- **FR-022**: 新增检查 MUST 通过项目既有的 `tools/dev` 统一入口运行，并受既有构建门禁约束（不允许以参数跳过测试或检查）；统一入口文档 MUST 同步说明新增命令。

**兼容性与交付**

- **FR-023**: 本次改动 MUST 保持现有全部本地测试分组通过、既有 CLI 命令输出与退出码不变、既有工作区定位规则不变、fat JAR 产物名称与启动方式不变。
- **FR-024**: 仓库 MUST 新增或更新工程基线说明，覆盖：门禁清单、本地命令、自动修复、例外登记、日志形态切换、健康与指标端点、CI 行为、`oryxos-init` Definition of Done 逐项核对结果。
- **FR-025**: 任何新增配置文件、工作流与脚本 MUST NOT 包含真实密钥、Webhook、主机地址等敏感信息；需要凭证的扫描（如漏洞库 API 密钥）MUST 通过环境变量或 CI 密钥注入。

### Key Entities

- **质量门禁（Quality Gate）**：一组在构建生命周期中串行执行的检查（格式、规约、静态安全、测试、依赖漏洞），每项有：名称、执行阶段、阻断级别、规则配置文件、豁免文件、对应本地命令与 CI 步骤。
- **追踪标识（Trace ID）**：一次 HTTP 请求的唯一标识，生命周期覆盖请求进入到响应写出，出现在该请求全部日志行与响应信封中。
- **运维端点（Operational Endpoint）**：健康（整体/存活/就绪）、信息、指标三类只读端点，与业务 API 分离，不进入业务 OpenAPI 契约，受与管理台一致的访问控制。
- **监控栈（Monitoring Stack）**：服务器上的 Prometheus（采集目标、采集间隔、保留期）与 Grafana（数据源、看板定义、访问入口），两者配置文件随仓库版本管理，凭证不入库。
- **例外登记（Suppression）**：对某条检查结果的有理由抑制记录，包含规则/漏洞标识、作用范围、理由、登记日期。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在开发者机器上，一条统一命令完成格式、规约、静态安全检查与全部本地测试；相比重构前的完整校验，新增检查带来的额外耗时不超过 3 分钟（依赖漏洞扫描已拆出为独立作业，不计入）。
- **SC-002**: 重构完成后，仓库内 100% 的 Java 源文件通过格式检查；对本次之后新增或修改代码的阻断级规约与静态安全违规数为 0；存量违规数量在工程基线说明中有记录且有清零计划。
- **SC-003**: 以生产形态启动服务后，任意抽取 100 行日志，100% 可被 JSON 解析且包含约定字段；对 10 个不同请求，用响应 `traceId` 在日志中检索，10/10 能命中且互不串扰。（度量对象为生产日志文件 `/var/log/oryxos/oryxos.json`；journal 中还会有 CLI 契约输出和 JVM 自身警告，按 FR-004 不改为 JSON，见 plan 偏差 D-2。US2 验收场景 1 的“服务输出”同此口径。）
- **SC-004**: 从服务器本机请求健康探针返回 UP、请求指标端点返回包含 JVM/HTTP 指标的文本；从公网未认证访问这些端点被拒绝（与 OpenAPI 文档接口相同策略）。
- **SC-005**: 已发布 OpenAPI 契约零差异测试继续通过；重构前后既有本地测试分组数量不减少、全部通过。
- **SC-006**: 在验证分支分别注入 1 处格式错误、1 处规约违规、1 处静态安全缺陷、1 个含已知高危 CVE 的依赖，4/4 被对应检查拦截并给出文件/行号或依赖坐标；提交前钩子拦截格式错误；CI 对未通过的推送标红。
- **SC-007**: 向 main 推送一次通过门禁的提交，部署工作流成功完成且服务器健康探针通过；服务器上的监控配置、看板与 systemd drop-in 与该提交仓库内容一致（逐文件校验和比对 100% 相同），OryxOS 输出 JSON 日志；除首次初始化与 nginx 规则外，无需任何手工登录服务器的操作。
- **SC-008**: 新开发者按工程基线说明在 30 分钟内完成：安装提交前钩子、运行一次完整校验、切换日志形态启动并检索一条追踪标识。
- **SC-009**: 在目标服务器上，运维人员通过受保护的入口打开 Grafana 看板，能看到最近 24 小时的 JVM 与 HTTP 指标曲线，数据间隔不超过 1 分钟；Prometheus 与 Grafana 常驻内存合计不超过 768MB（2026-11-23 由 512MB 调整：Grafana 13.3.1 实测常驻约 225–340MB，超出原 256MB 单项上限，维护者选择放宽），OryxOS 服务的堆上限保持不变；从公网未认证访问 Prometheus/Grafana 被拒绝。

## Assumptions

- 以 `oryxos-init` skill 的工具选型为既定输入：Google 格式（Spotless + google-java-format）、阿里 P3C（PMD 规则集）、Checkstyle、SpotBugs + Find Security Bugs、PMD、OWASP Dependency-Check、Actuator + Micrometer + Prometheus、Logstash Logback Encoder。具体版本在 plan 阶段核实与 Spring Boot 3.5.16 / JDK 21 的兼容性后锁定。
- "重构初始化代码"理解为补齐与整理工程地基（构建配置、日志、监控、规范与安全门禁、CI/钩子、基线文档），不改变五大核心能力的行为、不改变公开 REST 契约、不新增业务端点、不调整模块划分。
- 现有 `ApiResponse` 已含 `traceId` 字段；本次只改变其取值来源（与日志追踪标识一致），不改变字段名、类型或 OpenAPI schema。
- 现有 `/api/v1/health` 与 `/api/v1/info` 保留为业务契约端点，继续被发布脚本与管理台使用；新增的标准化运维端点与之并存，就绪判定复用同一运行时状态源。
- 日志持久化由应用文件日志承担（FR-001a），满足 002 规格 FR-005；不修改服务器系统级 journald 配置，journal 中的内容仅作快速排障用途，不承诺跨重启保留。
- 运维端点与业务端点共用同一监听地址与端口（回环），通过反向代理配置屏蔽公网访问；不引入独立管理端口。Prometheus 在本机回环地址直接采集，不经过 nginx。
- 测试代码纳入格式检查；编码规约与静态安全扫描对测试代码的阻断级别在 plan 阶段按规则组明确，默认测试代码放宽为报告级。
- 提交前钩子以仓库内脚本 + 一条安装命令实现（写入 `.git/hooks` 或配置 `core.hooksPath`），不要求安装 Python `pre-commit` 框架等全局工具。
- 持续集成在 GitHub Actions 上运行，新增的合并前工作流与现有部署工作流共享校验步骤；运行环境与现有部署工作流相同（Temurin 21、Maven 中央库镜像）。
- 目标服务器基线（2 核 4GiB、systemd、宝塔 nginx、JVM `-Xmx768m`）保持不变；新增指标采集的内存开销在 plan 阶段测量并记录。
- 监控栈只采集 OryxOS 自身指标与 Prometheus 自身指标；主机级指标（CPU、磁盘、网络）不在本次范围。
- 本次不实现：分布式链路追踪（OpenTelemetry 导出）、日志集中采集、告警规则与告警通知、GraalVM Native Image、多租户/认证/RBAC，以及任何业务功能变更。
- 本规格的行为验证依据是当前检出的代码与配置；历史文档中"已交付"的描述不作为现状依据。
